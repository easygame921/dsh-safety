# 静态 × 动态交叉验证（cross-validation）

> 生成时间：2026-08-16
> 目标：把静态（正则+AST）与动态（受限沙箱）两套引擎拧成一股绳——
> 静态 REVIEW 不再只是"需要人工看"，而是有动态证据支持的分级结论。

## 已完成

### 1. 核心模块 src/cross/validate.ts
- **威胁 → 动态证据映射**（REQUIREMENTS，T01-T14 全覆盖）：
  每条 review 规则定义"需要什么动态证据才算证实"
- **三态结论**：
  - `confirmed`（✅ 动态证实）：静态说 T06 读凭据，动态真的 fs-read 敏感路径
  - `unconfirmed`（⚠️ 未证实）：静态标风险但动态没触发——功能面噪音或未触发到
  - `no-dynamic`：未跑动态
- **关键设计**：安装期/声明期/prompt/client 层面的威胁（T03 安装脚本、T07 prompt 注入、
  T14 依赖链）动态沙箱观察不到——**维持 unconfirmed 而非"动态干净=安全"**（不误判）
- **动态额外发现**（升级信号）：动态暴露但静态没标 review 的行为
  （eval、敏感读取、命令、延迟触发敏感读取）

### 2. 接入
- **MCP**（server.ts）：auditContent 顺序 = 报告 → 🔀 交叉验证 → 动态轨迹 → 大白话
- **CLI**（cli.ts）：`audit <source> --dynamic` 附带动态 + 交叉验证
- 渲染：renderCrossValidation（表格：威胁/静态/结论/说明）

### 3. 测试 test/cross.test.mjs（4 项）
- 恶意 exfil：静态 T05/T06 → 动态 confirmed ✅
- 良性 ok-plugin：无动态证实（不误报）
- 无动态：verdict=no-dynamic 不崩
- T03 安装脚本：unconfirmed 不降级为安全（关键语义）

## 关键决策

- **unconfirmed ≠ 安全**：动态观察不到（T03/T07/T14 类）时绝不因"动态干净"降级——
  这是最容易犯的错误（"动态没抓到所以没事"）
- 证实判定用"敏感读取在网络上"等时序/组合，不只看单条轨迹
- 额外发现是升级信号：静态漏了但动态抓到（如延迟触发=反静态检测手法）
